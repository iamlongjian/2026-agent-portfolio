## 一句话定位

> **Quickstart 教你"怎么写"，这页教你"怎么想"** —— 拿到一个业务需求，怎么把它拆成一张能跑的图。

它用一个完整例子走了一遍：**客服邮件 Agent**（读邮件 → 分类 → 查文档 → 起草 → 转人工 → 发送）。

> ⚠️ 这个例子几乎就是电商客服工单的翻版，可直接映射到自己的业务。

---

## 核心：五步方法论

```
Step 1  拆步骤      → 每个步骤 = 一个节点，画出连接
Step 2  定类型      → 每步是哪种操作？需要什么上下文？
Step 3  设计 State  → 存什么、不存什么
Step 4  写节点      → 实现 + 处理错误
Step 5  接线        → 组装成图
```

**这五步是接任何业务需求的标准流程。**

---

## Step 1：拆步骤

把业务流程拆成**离散的、只做一件事**的步骤，每个变成一个节点。

官方示例：

```
START → 读邮件 → 分类意图 ─┬→ 查文档 ─┐
                          ├→ 建工单 ─┼→ 起草回复 ─┬→ 人工审核 → END
                          └→ 转人工 ─┘            └→ 直接发送 → END
```

**关键提醒（官方原话）**：

> 图里的箭头只是"可能的路径"，**实际走哪条由节点内部的逻辑决定**。

即：**图是骨架，决策在节点里。**

> 💡 注意区分：`分类意图`、`起草回复`、`人工审核` 会决定下一步去哪；而 `读邮件`、`查文档` 永远走向同一个下一步。

## Step 2：给每个节点定类型 ⭐

**全文最实用的框架**。每个节点归入四类之一：

| 类型 | 什么时候用 | 需要什么 |
| --- | --- | --- |
| **LLM 步骤** | 需要理解、分析、生成、推理决策 | 静态上下文（提示词）+ 动态上下文（state） |
| **数据步骤** | 需要从外部**读**数据 | 查询参数、重试策略、缓存策略 |
| **动作步骤** | 需要对外**做**事（发邮件、建工单） | 执行时机、重试策略、**不要缓存** |
| **用户输入步骤** | 需要人介入 | 决策上下文、期望的输入格式、触发条件 |

### 分类决定写法

- **LLM 步骤** → 关注提示词、state 里哪些字段要喂进去
- **数据步骤** → 关注超时、重试、缓存
- **动作步骤** → 关注幂等、执行时机（**动作不能重试过头**）
- **用户输入步骤** → 关注 `interrupt()` 和状态持久化

> **做方案时先给每个节点打上这四个标签，方案就清晰了。**

## Step 3：设计 State ⭐⭐

**两条判断标准（官方原文）**：

| 判断 | 处理 |
| --- | --- |
| 需要跨步骤持久化？ | ✅ **放入 state** |
| 能从其他数据推导出来？ | ❌ **不存，用时再算** |

示例里放了什么：

| 数据 | 为什么放 |
| --- | --- |
| 原始邮件、发件人 | 后面**重建不出来** |
| 分类结果 | 下游多个节点要用 |
| 搜索结果、客户数据 | 重新拉取**很贵** |
| 起草的回复 | 要经过审核，必须留存 |

### 核心原则：Keep state raw, format prompts on-demand

> **state 存原始数据，提示词在节点里现拼。**

好处：

- 不同节点可以按各自需要格式化同一份数据
- 改提示词不用改 state 结构
- 调试时能看清每个节点到底收到了什么

> 💡 **这条解释了 Quickstart 里的一个设计**：`SystemMessage` 为什么不在 state 里存着，而是在 `llmCall` 节点里临时创建？——因为它属于"提示词"，不属于"原始数据"。

## Step 4：写节点 + 处理错误 ⭐

**全文第二个最有价值的东西**，直接对应第 3 周容错任务：

| 错误类型 | 谁修 | 策略 | 什么时候用 |
| --- | --- | --- | --- |
| **瞬时错误**（网络、限流） | 系统自动 | `retryPolicy` 重试 | 重试通常就能好的 |
| **LLM 可恢复**（工具失败、解析错） | **LLM** | 错误写进 state，**循环回去** | 让模型看到错误自己调整 |
| **用户可修复**（缺信息、指令不清） | **人** | `interrupt()` 暂停 | 需要用户补充信息 |
| **重试后仍失败** | 开发者 | `error_handler` 补偿分支 | 兜底走另一条路 |
| **未知错误** | 开发者 | 让它冒泡上来 | 需要调试的 bug |

**关键认知：不是所有错误都该重试。** 分清五种情况，就不会一股脑 `try/catch`。

> 第 2、3 行就是**第 4 周 Human-in-the-loop** 的理论基础，现在有印象即可。

## Step 5：接线

把节点和边连起来。官方强调：

> **图结构是自然浮现的** —— 你只定义"必要的连接"，路由逻辑由节点自己处理。

好处：控制流显式、可追踪 —— **看当前节点，就知道下一步可能去哪。**

## Key Insights 六条（文末精华）

| # | 原则 | 含义 |
| --- | --- | --- |
| 1 | **拆成离散步骤** | 每节点只做一件事 → 能流式输出进度、能断点续跑、能清楚调试 |
| 2 | **State 是共享内存** | 存原始数据，不存格式化文本 |
| 3 | **节点就是函数** | 收 state → 干活 → 返回更新；需要路由时同时给出更新和去向 |
| 4 | **错误是流程的一部分** | 瞬时重试 / LLM 可恢复回环 / 用户可修复暂停 / 未知冒泡 |
| 5 | **人工输入是一等公民** | `interrupt()` 暂停、存全部状态、恢复时从原处继续 |
| 6 | **图结构自然浮现** | 你定义必要连接，节点自己管路由 |

## 进阶：节点粒度的权衡

为什么"读邮件"和"分类意图"不合成一个节点？两个权衡：

| 考虑 | 拆细的好处 |
| --- | --- |
| **韧性** | 每个节点边界都存 checkpoint；节点越小，失败时重复工作越少 |
| **可观测性** | 分类单独成节点，能看清模型到底判了什么 |

另一条经验：**调用外部 API 的步骤单独成节点** —— 能单独加重试策略，不连累别的节点。

> 官方标注"大多数应用可以跳过"，现在只需知道**存在这个权衡**。

### ③ 电商业务拆解

Step 2 的四种类型直接套：

```
售后工单 Agent
  读工单内容        → 数据步骤
  判断问题类型      → LLM 步骤
  查订单/物流/政策  → 数据步骤
  起草回复          → LLM 步骤
  退款/改价         ← 动作步骤 ⚠️ 必须加人工确认
  转人工            → 用户输入步骤
```
